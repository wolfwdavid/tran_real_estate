### Δ14: `text-label` token survives class merging (DEBT-06)

The defect `[CODE]`: `apps/web/src/lib/utils.ts:1-6` calls plain `twMerge`, which classifies `text-label` / `text-body` / `text-heading` / `text-display` as text-colour utilities. A later colour class (`text-muted-foreground`, `text-primary-foreground`, ...) then removes the size token: `twMerge('text-label text-muted-foreground')` returns `text-muted-foreground`. Badge (`components/ui/badge/badge.svelte:4-10`) therefore renders at the inherited size instead of Label 14px, and Button (`components/ui/button/button.svelte:6-17`) loses `text-body` (masked today because the inherited size is also 16px).

The contract:
1. **One** tailwind-merge configuration, extended with `classGroups: { 'font-size': [{ text: ['label', 'body', 'heading', 'display'] }] }` (the exact fix recorded in `04-*/deferred-items.md:3-12`), is used by both `cn()` and every `tv()` call. The four names are the full set of `--text-*` tokens in `app.css:37-46`; a token added later must be added to the group in the same commit.
2. `cn('text-label text-muted-foreground')` returns a string containing **both** classes. `cn('text-label text-sm')` keeps only `text-sm` (a later font-size wins, which is the correct merge semantics).
3. Computed result in real Chromium (`web-browser` project): a default `Badge` has `font-size: 14px`, `line-height` 19.6px (1.4), `font-weight: 600`; a default `Button` has `font-size: 16px`, `line-height` 25.6px (1.6), `font-weight: 600`. The test mounts each inside a container with `font-size: 20px` so an inherited size cannot pass by accident.
4. **Visible consequence, intended:** every `Badge` shrinks from the inherited size to Label 14/600, which is what the Phase 3 contract always specified. No layout is allowed to break from this: rows containing badges keep wrapping at 375px with no horizontal page scroll, and axe (`wcag2a, wcag2aa, wcag21aa, wcag22aa`) stays at zero violations across the copied-in primitives `[REQ]`. The Badge text/background pairs (`muted-foreground` on `surface`, `secondary` on `secondary-surface`, `foreground` on `accent-surface`) are already in the Phase 2-4 contrast matrices at 14px normal text (4.5:1 threshold), so no new contrast computation is needed.
5. The four existing workarounds (`FairHousingText.svelte:46`, `dropdown-menu-content.svelte:21`, `popover-content.svelte:22`, `StageBadge.svelte:4`) may be removed only if each removal is a line-local diff and the computed size is unchanged; otherwise they stay until after the Phase 16 codemod `[CTX D-15, Deferred]`.

## DEBT-02: Market Snapshot save-gate reason copy (spec-owned) Δ14

**Owner of the string:** this section. The plan copies these strings **verbatim** into `apps/web/src/lib/features/studio/snapshot/save-gate.ts` `[CTX D-13]`, and this section supersedes the single must-fix string in `09-UI-SPEC.md` §Copywriting "Market Snapshot builder", Step 4 "Gating reasons" (~line 611).

### The defect `[CODE]`

`save-gate.ts:39-40` builds one string from `mustFix`, and `saveGateReason` (`:50`) returns it when **either** `mustFix > 0` **or** `unackedReview`. A draft with only Review findings therefore reads "Fix the 0 items marked Must fix in the market notes, and review any others." (pinned by `save-gate.test.ts:60`), and a single Must fix reads "Fix the 1 items ...".

### Gating reasons, in priority order (first applicable reason is the visible line; `null` = Save allowed)

| # | Condition (`SaveGateState`) | Reason line (exact) |
|---|-----------------------------|---------------------|
| 1 | `!hasData` | Load a ZIP code's data first. *(unchanged)* |
| 2 | `dataSections < 1` | Choose at least one section with market data. *(unchanged)* |
| 3 | `notesOn && notesStatus !== 'ready'` | Draft the market notes, or turn them off in step 2. *(unchanged)* |
| 4a | `notesOn && mustFix === 1` | **Fix the 1 item marked Must fix in the market notes, and review any others.** |
| 4b | `notesOn && mustFix >= 2` | **Fix the {n} items marked Must fix in the market notes, and review any others.** (`{n}` as a plain integer, no thousands separator needed in practice) |
| 4c | `notesOn && mustFix === 0 && unackedReview` | **Review the flagged phrases in the market notes and check the box in step 3 to continue.** |
| 5 | `live && profileMissing.length > 0` | Add your {fields joined with ", "} in your profile so your disclosure can be added. *(unchanged)* |

Rules:
- **Never "Fix the 0 items".** The must-fix builder is only reached with `mustFix >= 1`; a review-only state always yields 4c. A unit case for 0 (review-only), 1 (singular), and 2+ (plural) is required `[REQ DEBT-02]`, and the existing `save-gate.test.ts:60` expectation flips from `R.fix(0)` to the 4c string.
- **"items", not "phrases", in 4a/4b:** Must fix findings in the notes include the Phase 7 number check ("Number not in this report"), which is a number, not a phrase. **"phrases" in 4c:** only Fair Housing Review findings produce an unacknowledged-review state.
- 4c names the control the user must act on. The acknowledgement checkbox is the Phase 5 `FindingsSummary` box inside the step 3 notes panel (`apps/web/src/lib/ai/ui/FindingsSummary.svelte:86-87`, label "I've reviewed the flagged phrases. They describe the property, not who should live there."). The string mirrors the Phase 5 panel reason `WARN_REASON` ("Review the flagged phrases and check the box above to continue.", `apps/web/src/lib/ai/ui/panel-controller.ts:31`), with "above" replaced by "in step 3" because the Save button sits in step 4, outside the panel.
- Shape follows `panel-controller.ts:31-37`: a constant for the review-only string and a pluralizing function for the must-fix string (`n === 1 ? singular : plural`). Constant/function names are the planner's choice; keep `notesFindingsReason`'s export name if that keeps the diff line-local `[CTX D-15]`.
- While any Must fix remains, `notesGateFields` already reports `unackedReview: false` (`save-gate.ts:80`), so 4a/4b keep the "and review any others" tail and 4c never shows alongside them.

### Interaction contract (unchanged from `[P9]`, restated for the new E2E)

| State | Save button | Reason line | Focus / announcement |
|-------|-------------|-------------|----------------------|
| Review-only, unacknowledged | `aria-disabled="true"`, Phase 3 disabled visuals, `aria-describedby` → reason line | 4c string, Label 14/600 `foreground`, `tabindex="-1"`, `data-save-reason` (`SnapshotBuilder.svelte:530-538`) | Activating Save moves focus to the reason line and announces the visible reason through `LiveAnnouncer` (`refuse()`, `SnapshotBuilder.svelte:307-309`); URL stays on `/agent/studio/snapshot/` |
| Box checked in step 3 (no other reason applies) | Enabled (no `aria-disabled`) | Removed | No announcement on clearing (never announce a gate clearing `[P9]`) |
| Review phrase typed while editing (urgent path, `SnapshotBuilder.svelte:345-359`) | Refused immediately, not after the 300 ms recheck | 4c (or 4a/4b if a Must fix is typed) | Same as row 1 |

E2E requirement `[REQ DEBT-02]`: on a warn-only draft (e.g. the existing "Walking distance to church." plant, `tests/e2e/snapshot-builder.spec.ts:195`), assert the **full 4c string** with `toHaveText`, that a Save activation is refused (focus on the reason, URL unchanged), then check the step 3 box and assert Save enables. The comment at `snapshot-builder.spec.ts:198-199` ("do not lock it in here") is removed. **Planner note:** `NOTES_REASON` at `snapshot-builder.spec.ts:40` (`/Fix the \d+ items marked Must fix in the market notes/`) must become `/Fix the \d+ items? marked Must fix in the market notes/` (or an exact singular string) because the planted `$9,999` case produces exactly one Must fix and now reads "1 item".

A phrase that is both an advertising claim and advice language keeps **both** reasons listed in the investor memo gate. No change to `apps/web/src/lib/features/investor/memo/memo-checks.ts` or its copy `[CTX D-03]`.

### Lazy validation `[D]` (Claude's Discretion area `[CTX]`)

| Check | Where it runs | Why |
|-------|---------------|-----|
| Empty message, email shape (`validateEmail`), honeypot and 3-second timing (`gateSubmit`), counter threshold | **Inline**, from `form-gate.ts` and `feedback-counter.ts` (plain validators, no zod) | Instant feedback on blur and submit, no network or chunk needed |
| API-key scan (`findKeyMaterial`, feedback only) | **Lazy**: `await import('@tran/core/backup')` on submit | Pulls zod |
| Sender (`submitOwnerForm`) | **Lazy**: `await import('$lib/leads/owner-forms')` on submit | Pulls the sink and `lead-block` (zod/mini) |

Rules:
1. **Order is unchanged** `[P10]`: inline validation → key scan → honeypot/timing gate → one request. The key scan always completes before any request; nothing is sent while it is pending.
2. **Warm-up:** the first `focusin` or `pointerdown` inside the open form starts both imports (fire-and-forget, once per mount), so by the time the visitor submits the chunks are usually cached. Submit awaits the same promises.
3. **Busy state:** from the moment inline validation passes until the request settles (including any wait on the lazy chunks), the form is `aria-busy="true"`, the fields and button are disabled, and the button shows the existing in-progress label (**Sending…** / **Joining…**) with the spinner. No new label is introduced.
4. **Fail closed:** if a lazy import rejects (offline, or a stale chunk after a redeploy), nothing is sent. The form shows the existing network error (title "Your message wasn't sent" / "Your email wasn't sent", body "Check your connection, then try again. Nothing was saved.", plus the contact line when set), announces "{title}. {body}", and returns focus to the submit button, exactly as a network failure does today. The cached promise is cleared so the next submit retries the import.
5. **No lazy rendering of the form itself.** The prerendered markup is complete and the same size before and after hydration, so there is no placeholder and no added layout shift (CLS stays below 0.1 at 375×812 and 1280×800; `cls.json` gains these four routes if the audit does not already measure them).
6. Key found → the existing field error on **Your feedback** ("This looks like it contains an API key. Remove it, then send again."), focus to the textarea, busy state cleared.
