<decided_semantics>
The check-on-open pass is per DataShell mount (= per app open / full page load), as today. The new
rule only decides WHEN in that mount it may start:

1. `runAlerts` (DataShell prop, default `true` so the harness and any other caller keep today's
   behavior). The (app) layout passes `runAlerts = !isAgentCrm(page.route.id)` using the SAME
   `isAgentCrm` it already uses for the status bar. So: false on `/agent/` and every
   `/agent/*` CRM route; true on renter, investor, settings, `/agent/studio/*` (Phase 9, which
   does use RentCast) and any unmatched route (route id null), exactly the routes where it runs
   today.
2. runtime.start() still runs on mount on every route (the cap-prompt host and the meter need it).
   Only the saved-search pass is gated.
3. The pass starts at the first moment BOTH hold: start() has resolved AND runAlerts is true.
   - Opened on renter/investor/settings: starts right after start() resolves, from the onMount
     boot, exactly as today (unchanged timing, unchanged once-per-open).
   - Opened on an agent CRM page: no pass. On the first client-side navigation to a non-agent
     (app) route in the same mount, the pass starts once there (1-3 due run silently and announce;
     4+ open the DueSearchesDialog; at the cap they wait), where the status bar is visible.
   - Never more than one pass per mount: a synchronous latch (`alertsClaimed`) is set before the
     pass starts. Navigating agent -> renter -> agent -> renter runs nothing the second time
     (same as today's "once per open"; the next full load is the next open).
4. Withdraw on leave: if runAlerts becomes false while the DueSearchesDialog is still waiting for
   an answer (only reachable by browser Back/Forward or a programmatic goto, since the dialog is
   modal), DataShell closes the dialog and settles the confirm as declined (`settleDue(false)`):
   zero calls, the scheduler records the decline, Tran asks again on the next open. No
   DUE_DECLINED announcement (the user did not press Not now). A pass the user ALREADY confirmed
   (progress showing) is not cancelled: it was authorized on a non-agent page and runs to the end.
5. Full page loads of /agent/* URLs are fresh mounts, so each one starts with runAlerts false and
   never runs a pass.

Why a `$effect` is acceptable for the deferred start (record this in the code comment): the
04-07 rule is "reactive re-runs must never spend". The effect here only calls `untrack(startAlerts)`;
the latch, not the effect, is the spend guard, so any number of effect re-runs start at most one
pass, and the spend itself happens inside the scheduler after awaits, outside any tracking
context. The ESLint selector (callee object named *gateway/*scheduler) is not triggered and must
NOT be disabled. A component test toggles runAlerts repeatedly and proves one pass.
</decided_semantics>
