### Locked Decisions

The owner chose fully autonomous mode on 2026-10-04. Researched recommended defaults are adopted.

#### Gateway & budget
- **Single gateway module** at `apps/web/src/lib/data/` wrapping a typed RentCast client (`X-Api-Key` header only; GET only; Zod-mini response schemas; mappers to normalized domain rows in `packages/core`).
- **Budget math lives in `packages/core`** (pure, tested): ledger of billed calls per calendar month (UTC, matching RentCast's cycle approximation), cap check, projected-burn estimate.
- **Only HTTP 200 responses count as billed** (RentCast bills successful requests). 404 "no results" is negatively cached for its TTL and recorded as unbilled unless Phase 4 research with a real key proves otherwise; the ledger stores both counts so the policy can flip without a migration.
- **Hard cap:** default 40 of 50, user-editable in Settings (1..50; values above the plan limit need a typed confirmation). When the next call would exceed the cap, the gateway throws `BudgetCapReached`; the UI shows a confirm dialog ("This call goes past your cap. RentCast bills overage at $0.20 per call.") with an explicit "Spend 1 call anyway" action. Confirmation is per call, never remembered.
- **Call cost preview:** every call-spending control carries a `(N calls)` label derived from the gateway's `estimateCost(request)`; reads served from cache show `(0 calls · cached)`.
- **No auto-pagination, no reactive refetch.** `$effect` must never call the gateway directly; views read from cache-backed stores and only explicit user actions (search, Refresh, scheduled alert run) spend calls. A lint rule / unit test guards this.
- **Cache:** Dexie table `apiCache` keyed by canonical request key; per-endpoint TTLs (listings 24h, estimates 7d, market stats 30d, 404 negative 24h). "Refresh (1 call)" bypasses TTL for one request.
- **Alerts scheduler:** on app open, saved searches with `lastRunAt` older than 24h are due; they run sequentially, each at most once per 24h, and if more than 3 are due the user confirms the total cost first. Diffing (`new / price-changed / gone`) is `core.diffSnapshots`.

## Summary

RentCast is a plain GET + `X-Api-Key` REST API. Its documentation (downloaded today as markdown from `developers.rentcast.io/reference/*.md`) confirms the facts the budget design depends on. A "successful API request", which is the only kind billed, is "an HTTP request … that returns a 200 status code and a response body". "You will also not be billed for requests that return an error (a status code other than 200)." RentCast does "not currently support hard usage caps or automatic API request blocking", and it recommends that integrators build their own request blocking, which is exactly this phase. The Developer plan is $0 for 50 requests a month, with overage at $0.20 per request. Paid plans have lower overage rates: Foundation $0.06, Growth $0.03, Scale $0.015. Rate limit: 20 requests per second per key (`429 auth/rate-limit-exceeded`). Bulk endpoints return at most 500 rows (`limit` 1..500, default 50), and every page is a separate billed request.

Live keyless probes run today (they cannot bill anything) show two useful things. First, RentCast checks authentication before parameter validation: a bogus key on `limit=0`, `limit=501`, `zipCode=abc`, or an AVM call with no address always returns `401 auth/api-key-invalid`, never `400`. Second, CORS still returns `Access-Control-Allow-Origin: *` with `x-api-key` as the only allowed request header, and no `Access-Control-Expose-Headers`. So `Retry-After`, `X-Total-Count`, `X-Limit`, and `X-Offset` cannot be read from the browser. That makes a zero-cost key test straightforward. Send a request that cannot return data, `GET /v1/markets?zipCode=00000`. Then `400`/`404` means the key is valid (never billed), `401` means invalid, `403` means restricted or billing, and `429` means rate limited. The docs also expose `suppressLogging=true` on every endpoint (added 2025-08). Tran should send it on every call, because user addresses are search inputs.

The gateway design is ports-and-adapters:
- **Pure logic in `packages/core`:** the canonical key, TTL table, error classification, budget period/meter/projection, location parsing, listing filters, `diffSnapshots`, and due-search planning.
- **The web gateway in `apps/web/src/lib/data/`:** owns Dexie I/O (`apiCache`, an append-only `ledger`, `savedSearches`/`searchSnapshots`), in-flight dedupe, and mode selection.
- **The cap:** enforced by a reserve-then-fetch step inside a single Dexie read-write transaction. IndexedDB serializes overlapping read-write transactions across tabs, so two tabs cannot both take call #40.
- **The ledger:** stores the HTTP status of each call, not a precomputed "billed" flag. "Billed" is derived by a policy function, so flipping the 404 policy after the real-key UAT is a one-line change with no migration.
- **Sample mode:** routes the same RentCast client through an in-memory fixture `fetch` that returns RentCast-shaped JSON. The Zod schemas and mappers therefore run identically on fixtures and live data, and the fixtures double as schema tests. Fixture dates are stored relative to an anchor and rebased at load time, so "listed within 7 days" and "new since last visit" keep working on sample data forever.

**Primary recommendation:**
- Build `core` first: budget, keys, errors, location, diff, schedule. Then build the RentCast client and schemas, then the gateway with the ledger-reservation transaction, then the fixture generator, guard extension and fixture fetch, then the scheduler, then UI primitives.
- Test every spend path with an injected clock and an injected `fetch` spy over a fresh `fake-indexeddb` factory per test. Never call `vi.useFakeTimers()` with default options, because it deadlocks fake-indexeddb.
- Probe keys with `GET /v1/markets?zipCode=00000&suppressLogging=true`.

### Pattern 1: Canonical request key
**What:** One pure function turns `(endpoint, params)` into a stable string. Identical intent gives an identical key, and the key is the cache primary key, the dedupe key and the ledger reference.
**Rules:**
- Drop `undefined`, `null` and `''`.
- Drop transport-only params (`suppressLogging`, `includeTotalCount`).
- Never include the API key.
- Normalize values the way the client will send them: city title-cased, state uppercased, ZIP 5-digit, numbers as decimal strings, ranges as `min:max` with `*`, multi-values sorted and pipe-joined.
- Sort the remaining params by name.
- `encodeURIComponent` each value.
- Prefix with the endpoint id.

The client builds its URL from the same normalized params, so the cache key and the wire request can't drift.

**Fetch wide, filter local (recommended default for listings):**
- The listings request key holds geography + `status=Active` + `limit=500` + `offset=0`.
- Filters (price, beds, baths, property type, daysOld) are applied locally by `core.filterListings`. Changing a price slider costs 0 calls, and several saved searches in one ZIP share one call.
- If a response has exactly 500 rows, set `truncated: true`. Phases 6/7 then show "Showing the 500 most recently seen listings here; search a ZIP for full coverage".
- Send `propertyType` server-side only for sale `Land` (rare).

This is a planner decision inside "Claude's Discretion". If declined, include all filters in the key and accept a per-filter call cost.

```ts
// packages/core/src/data/canonical.ts  (sketch)
export type ParamValue = string | number | boolean | readonly (string | number)[] | undefined | null;
const TRANSPORT_ONLY = new Set(['suppressLogging', 'includeTotalCount']);
export function canonicalParams(params: Record<string, ParamValue>): [string, string][] {
	return Object.entries(params)
		.filter(([k, v]) => !TRANSPORT_ONLY.has(k) && v !== undefined && v !== null && v !== '')
		.map(([k, v]) => [k, Array.isArray(v) ? [...v].map(String).sort().join('|') : String(v)] as [string, string])
		.sort(([a], [b]) => (a < b ? -1 : a > b ? 1 : 0));
}
export const canonicalKey = (endpoint: EndpointId, params: Record<string, ParamValue>) =>
	`${endpoint}?${canonicalParams(params).map(([k, v]) => `${k}=${encodeURIComponent(v)}`).join('&')}`;
```

### Pattern 2: Append-only ledger with reserve-then-settle (the cap)
**What:**
- Each spend attempt writes one ledger row **inside the same Dexie `rw` transaction that checks the cap**.
- The row starts as `status: 'pending'`. After the response it is settled to the HTTP status (`200`, `404`, `401`, …, or `0` for a thrown fetch).
- "Billed" is never stored. `core.isBilled(status)` derives it at read time, so the 404 policy flips with a one-line change and no migration.
- A `pending` row older than 2 minutes (tab closed mid-request) counts as billed (conservative).

**Why a transaction:** IndexedDB runs read-write transactions with overlapping scopes in order, across all connections of the origin. So two tabs at 39/40 cannot both reserve call #40. HIGH (IndexedDB spec: "readwrite transactions with overlapping scopes are run in order").

**Row shape:** `{ id: uuid, periodKey: '2026-10', at: epochMs, endpoint, key: canonicalKey, intent: 'user'|'refresh'|'scheduler'|'key-test', status: 'pending'|number, overCap: boolean, settledAt? }` plus Phase 3's `Syncable` fields. Indexes: `'id, periodKey, [periodKey+at]'`.

```ts
// apps/web/src/lib/data/ledger-repo.ts (sketch)
async function reserve(req: SpendRequest, grant?: OverCapGrant): Promise<string> {
	return db.transaction('rw', db.ledger, db.prefs, async () => {
		const now = clock();
		const period = periodKey(now);
		const rows = await db.ledger.where('periodKey').equals(period).toArray();
		const used = summarize(rows, now).countedTowardCap; // billed + pending (+ stale pending)
		const cap = await readCap(); // pref, default 40
		const overCap = used + 1 > cap;
		if (overCap && !(grant && consume(grant, req.key))) throw new BudgetCapReached({ used, cap, cost: 1 });
		const id = crypto.randomUUID();
		await db.ledger.add({ id, periodKey: period, at: now, endpoint: req.endpoint, key: req.key,
			intent: req.intent, status: 'pending', overCap /* + Syncable fields */ });
		return id;
	});
}
```
**Single-use grant:**
- `CapConfirmDialog` → `const grant = gateway.grantOverCap(requestKey)`. The object is bound to one canonical key and has a `consumed` flag. `consume()` flips the flag inside the reservation.
- A second call without a new grant throws again (UI-SPEC test). The grant lives only in memory and is never persisted.
- The scheduler never receives a grant.

### Pattern 3: Gateway read/spend split
- `peek(request)`: cache only, never spends, **the only method views and `$derived`/`$effect` code may use**. It returns `{rows, provenance:{source, fetchedAt, stale}} | {error: NoResults (cached 404)} | undefined`.
- `estimateCost(request)`: `0` if sample mode, `0` if there is a fresh cache entry (positive or negative), otherwise `1`. It returns `{calls, reason: 'sample'|'cached'|'network'}`, and `CostLabel` formats from `reason`.
- `estimateBatchCost(requests)`: number of **unique** canonical keys not freshly cached (for `DueSearchesDialog`).
- `get(request, opts?)`: fresh cache → return it (0 calls, original `fetchedAt`). Otherwise in-flight dedupe map → reserve → client → settle → cache put → return.
- `refresh(request, opts?)`: like `get` but skips the TTL check (still deduped, still capped).
- `testKey()`: probe (Pattern 6). Bypasses cache and cap. Still writes a ledger row, so an unexpected `200` is counted.
- **Sample mode:**
  - Same client over `fixtureFetch`.
  - **No ledger and no cap.**
  - **No `apiCache` writes.** Fixtures are in memory, and caching them would risk serving sample rows as "live" after a mode switch.
  - Provenance `source:'sample'`.
- **In-flight dedupe:** `Map<key, Promise>` per gateway instance, deleted in `finally`. Two clicks or two components asking for the same key share one call and one ledger row.
- **Serialization:** a simple promise queue (concurrency 1) for live calls, so the 20 req/s limit is never approached and the scheduler is naturally sequential.
- **Reactive guard (defense in depth):** `get`/`refresh` throw `ReactiveSpendError` when `inReactiveContext()` is true (`$effect.tracking()`, verified in the Svelte docs). It is injected so Node tests can stub it. It catches a synchronous call at the top of an effect. It cannot catch calls after an `await` (tracking is off there), which is why the lint rule exists too.

### Pattern 4: Fixture `fetch` (sample mode through the real client)
```ts
// apps/web/src/lib/data/fixtures/fixture-fetch.ts (sketch)
export function createFixtureFetch(data: FixtureSet, now: () => number): typeof fetch {
	const shift = now() - Date.parse(data.meta.anchor); // rebase all dates (Pattern 5)
	return async (input) => {
		const url = new URL(typeof input === 'string' ? input : input instanceof URL ? input.href : input.url);
		const route = matchRoute(url.pathname);            // '/v1/listings/rental/long-term' → 'rental-listings'
		const result = route ? query(route, url.searchParams, data, shift) : { status: 404 };
		return new Response(result.status === 200 ? JSON.stringify(result.body) : JSON.stringify(errorBody(result.status)),
			{ status: result.status, headers: { 'content-type': 'application/json' } });
	};
}
```
- `query` applies RentCast semantics: location match (zip, or case-sensitive city/state), `status`, ranges, `limit`/`offset`, sort by `lastSeenDate` desc. Empty → `404`.
- A location outside the 3 sample metros → `404` with `{error:'sample/outside-coverage'}`. Tran maps it to `NoResults` with `reason:'outside-sample-coverage'`, so a portal can say which metros exist (Open Q3).
- **Never relabel fixture rows with a real city the user typed.**
- Load fixtures by dynamic `import()` inside the gateway factory, so marketing routes never pull them. Phase 1's ESLint boundary already bans `$lib/data` from `(marketing)`.

### Pattern 5: Deterministic generator + anchor rebasing
- `scripts/gen-fixtures.mjs`:
  - Node built-ins only plus a seeded PRNG (mulberry32 or sfc32, about 10 lines).
  - Fixed seed and `ANCHOR = '2026-10-01T00:00:00.000Z'`.
  - Writes every file through **Prettier's API** with the repo config, because `pnpm lint` runs `prettier --check .` and `JSON.stringify(…, '\t')` is not Prettier-stable for short arrays.
  - A `--check` mode regenerates in memory and diffs against disk. CI/unit test: fixtures are byte-identical to the generator output, so no hand edits.
- All dates are generated relative to `ANCHOR`. `fixture-fetch` adds `shift = now − ANCHOR` to every ISO date field (`listedDate`, `createdDate`, `lastSeenDate`, `removedDate`, `history` keys, AVM comps `listedDate`/`lastSeenDate`). For market history `YYYY-MM` keys, it shifts by whole months. `daysOnMarket`/`daysOld` stay as generated, since they are relative already.

### Pattern 6: Zero-cost key probe
- **Request:** `GET https://api.rentcast.io/v1/markets?zipCode=00000&dataType=Rental&historyRange=1&suppressLogging=true` with the key header. ZIP 00000 has never been assigned, so RentCast has no data to return. Keep it as **one exported constant** so UAT can swap it.
- **Classification:**

| Response | Result |
|---|---|
| `400` or `404` | `valid` (never billed) |
| `200` | `valid-billed` (ledger counts it; UI-SPEC already has the "counted as 1 call" copy) |
| `401` | `invalid` |
| `403` | `restricted` |
| `429` | `rate-limited` |
| fetch throws or 5xx | `unverified` |

- **Why it's sound:** auth is evaluated before parameter validation (live-verified today). An invalid key therefore can't masquerade as "valid" through a 400.
- **Not yet verified:** whether an **endpoint-restricted** valid key gets 403 before or after validation. The worst case is a key that excludes `/markets` reading as `valid`. This goes to UAT.
- **Format check before any request:** trimmed, non-empty, no whitespace, printable ASCII, length 16..128. Do **not** assume a hex/32-char format; the real format is a UAT item.

### Pattern 7: Alerts scheduler (two cursors, claim-then-run)
- **SavedSearch:** `{ id, portal, name, request /* canonical params */, lastRunAt: number|null, lastSeenAt: number|null, claimedAt: number|null, ...Syncable }`.
- **Snapshot:** `searchSnapshots`, keyed by `searchId`: `{ searchId, takenAt, truncated, items: Record<listingId, {price, status, firstSeenAt}> }`.
- **Due:** `lastRunAt === null || now − lastRunAt ≥ 24h`, and not claimed in the last 2 minutes.
- **`planRun(due, {used, cap, mode})`:**
  1. Sort by `lastRunAt` ascending (oldest first).
  2. Compute `cost = estimateBatchCost`.
  3. `k = max(cap − used, 0)` calls are available. Take searches in order while their marginal cost fits.
  4. `needsConfirm = due.length > 3` (the CONTEXT rule: count of due searches, not calls).
  5. If `used ≥ cap`, run none (`DataStatusBar` "weren't checked" line).
- **Run:**
  - For each planned search, **claim** in an `rw` transaction (re-check due + unclaimed, set `claimedAt = now`), then call `gateway.get(request, {intent:'scheduler'})`, never `refresh`. A sibling search that just fetched the same key costs 0.
  - Diff against the snapshot with `core.diffSnapshots`, then write the snapshot plus `lastRunAt = now` in one transaction.
  - Sequential `for … of` with `await`.
  - `BudgetCapReached` mid-run stops the loop. The rest wait. It is never surfaced as a dialog.
- **Mode:** sample mode runs on fixtures (0 calls, no dialog). Live mode only runs when the key is unlocked.
- **"N new since last visit":** items with `firstSeenAt > lastSeenAt`. `lastSeenAt` advances only when the user opens that search's results (explicit), never on app open.
- **Cross-tab:** the claim transaction prevents double runs. Optionally wrap the whole pass in `navigator.locks.request('tran-alerts', {ifAvailable:true}, …)` (Chrome 69+, Firefox 96+, Safari 15.4+), injected so Node tests use a no-op.

**`diffSnapshots(prev, next, opts)`:**
- `new` = ids in next and not in prev.
- `priceChanged` = ids in both with a different `price`. Keep `{from, to}`.
- `gone` = ids in prev and not in next, **only when `next.truncated === false`**. Otherwise they are "unknown", because they may have fallen outside the 500-row window. An item that is present with `status === 'Inactive'` or a non-null `removedDate` also counts as gone.
- `firstSeenAt` carries over for kept items.

### Pattern 8: Location normalization (no external API)
`parseLocation(input)`:
1. Trim and collapse whitespace.
2. `^\d{5}(-\d{4})?$` → `{kind:'zip', zip: first5}`. Reject `00000`.
3. Otherwise split on the last comma, or on the last whitespace token if there is no comma. The tail must resolve to a state through the 50-states + DC table (abbreviation, case-insensitive, or full name, e.g. "Texas"/"new york").
4. City = head, title-cased per word and per hyphen segment ("winston-salem" → "Winston-Salem"), keeping user punctuation ("st. louis" → "St. Louis"). `Mc` + letter is capitalized ("mcallen" → "McAllen"). `Mac` is left alone ("Macon").

RentCast's city param is case-sensitive, and its 2025-08 parser is "more tolerant of malformed addresses", but the docs still say case-sensitive. Title-casing will miss names like "DeKalb" or "LaGrange". The `NoResults` copy already says "Try a nearby ZIP code". Portals should prefer ZIP input and show the parsed form ("Searching Austin, TX") before spending.

### Pattern 9: Zod-mini tolerant schemas
- Use `z.object` (unknown keys stripped, so extra RentCast fields never fail).
- **Required:**
  - Listings: `id`, `price` (number), `status` (string), `zipCode`, plus `formattedAddress` or `addressLine1`.
  - AVM: `rent` or `price`.
  - Markets: `zipCode`.
- **Everything else:** `z.nullish(...)`.
- Enum-like fields (`propertyType`, `listingType`, `status`) are `z.string()`. The **mapper** normalizes unknown values to `'Other'`, so a new RentCast enum value is never a `SchemaMismatch`.
- **Arrays:** validate per row. Drop failing rows and count them (`droppedRows`). Raise `SchemaMismatch` only if the top-level shape is wrong (for example, not an array) or **every** row failed. The call is still billed, per the UI copy.
- **What the cache stores:** the **validated raw payload**, not the mapped domain rows. A later mapper change then costs 0 calls (map on read).
- **Locale:** zod/mini doesn't load locale messages by default. Tran never shows Zod messages; `SchemaMismatch` carries issue paths for the console only, never the payload (PII).

### Anti-Patterns to Avoid
- **Calling `gateway.get/refresh` from `$effect`, `$derived`, `onMount` or a template expression.** Views call `peek()`. Only click handlers and the scheduler spend.
- **Auto-pagination or "load all".** One page per explicit action. A later "Load more (1 call)" is a portal decision.
- **Storing a `billed` boolean.** Store the status. Derive billing.
- **Caching sample-mode responses in `apiCache`**, or sharing keys between modes.
- **Reading `Retry-After` / `X-Total-Count`.** They are not exposed (no `Access-Control-Expose-Headers`).
- **Adding request headers beyond `X-Api-Key` and `Accept`.** The preflight allows only `x-api-key`, and anything else fails CORS.
- **Putting the API key in the URL, cache key, ledger row, error message or console.**
- **`window.confirm`** (already lint-banned in Phase 3).

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Cross-tab atomic cap check | localStorage counters, BroadcastChannel "locks" | One Dexie `rw` transaction over `ledger` (+ prefs) | IndexedDB serializes overlapping rw transactions across connections. Hand-rolled locks race |
| IndexedDB in unit tests | Mocks of Dexie methods | `fake-indexeddb` `new IDBFactory()` per test, passed to `new Dexie(name, { indexedDB, IDBKeyRange })` | Real transaction semantics, so the concurrency test is meaningful |
| Response validation | `typeof` ladders | `zod/mini` | Already in the stack. Gives issue paths for `SchemaMismatch` |
| JSON fixture formatting | Custom pretty-printer | `prettier.format(…, { parser: 'json', ...resolvedConfig })` in the generator | `prettier --check .` must pass on generated files |
| Relative time | Manual math | `date-fns` `formatDistanceToNowStrict` (UI-SPEC) | Pluralization/rounding |
| PII scan | A second scanner | Extend `scripts/lib/real-data-rules.mjs` (`findProblems`) | One rules module, already unit-tested and wired into pre-commit, CI hygiene and `pnpm guard` |
| Accessible confirm dialogs | Custom focus traps | Phase 3 `ConfirmDialog` / bits-ui `AlertDialog` | Focus return, Escape handling |
| Seeded randomness | `Math.random` | ~10-line mulberry32/sfc32 in the generator | Determinism, so fixtures are reproducible and reviewable |

**Key insight:** every hard part here (atomic budget, cache invalidation, schema drift) already has a primitive in the stack. The risk is in **wiring**: a single path that bypasses the gateway, or a reactive read that spends. Tests and lint have to target the wiring, not just the pure functions.

## Common Pitfalls

### Pitfall 1: `vi.useFakeTimers()` deadlocks fake-indexeddb
**What goes wrong:** Dexie promises never resolve, and tests time out.
**Why:** `fake-indexeddb@6.2.5` `lib/scheduling.js` resolves `globalThis.setImmediate || … || setTimeout` **at call time** (verified in the tarball today). Vitest's default fake timers replace `setImmediate`/`setTimeout`.
**How to avoid:** Inject `clock: () => number` into the gateway, ledger, scheduler and fixture fetch. Advance a plain variable in tests. If a test truly needs fake timers (the 429 countdown UI), use `vi.useFakeTimers({ toFake: ['Date'] })` or keep it in a test with no IDB.
**Warning sign:** A Dexie test hangs exactly at the first `await db.…`.

### Pitfall 2: The "10 re-renders spend 0" test is vacuous if the view uses `peek` by construction
**What goes wrong:** The test passes even if a future refactor moves a `get()` into an `$effect`.
**How to avoid:** Use three layers:
1. A lint selector that bans gateway spend calls inside `$effect(...)`/`$effect.pre(...)` callbacks (below).
2. The runtime `$effect.tracking()` guard throwing `ReactiveSpendError`.
3. A browser component test that renders a harness component 10× via `rerender()` with a spy `fetch`. **Prove non-vacuity:** a mutant harness that calls `get()` inside `$effect` must fail (spy count > 0 or `ReactiveSpendError`). Keep the mutant as a test fixture string compiled in-test, or as a second harness file used only by the test.

**Lint selector** (add to the shared `no-restricted-syntax` array, see Pitfall 6):
```js
{
	selector:
		"CallExpression:matches([callee.name='$effect'], [callee.object.name='$effect']) CallExpression[callee.property.name=/^(get|refresh|testKey|runDue|runDueSearches)$/][callee.object.name=/(gateway|scheduler)$/i]",
	message: 'Never spend RentCast calls from $effect. Read with gateway.peek() and spend only in event handlers or the scheduler.'
}
```

### Pitfall 3: Two tabs, one cap
**What goes wrong:** Both tabs read `used = 39` and both call, giving 41/40. Two tabs run the scheduler on open and double-run due searches.
**How to avoid:** Pattern 2 reservation transaction and Pattern 7 claim transaction.
**Test (mutation-proven, per owner feedback "mutation-test the concurrency guards"):**
- Two gateway instances share one `IDBFactory`, start at 39/40, and fire concurrently.
- Expect exactly 1 fetch and 1 `BudgetCapReached`.
- Then mutate the reservation (move the count outside the transaction) and confirm the test goes red.
- Same for two schedulers: 5 due searches → exactly 5 fetches total.

### Pitfall 4: Sample rows served as live after a mode switch
**How to avoid:** No `apiCache` writes in sample mode. Provenance is set by the gateway mode, never by the payload.
**Test:** Run a sample search, switch to live with a key, then call `peek` on the same request → `undefined`, and `estimateCost` → 1.

### Pitfall 5: The guard scans more than fixtures
**What goes wrong:** `DATA_PATH = /(^|\/)(fixtures?|data|mocks?|samples?|seed)(\/|$)/i` matches **all of `apps/web/src/lib/data/**` and `lib/features/shared/data/**`**. Any test, source or Svelte file there containing a real-looking email or phone fails `pnpm guard` and the pre-commit hook. Test files with a bogus RentCast phone like `"5129948203"` (the docs' example format) would fail.
**How to avoid:**
- Build every planted PII value from fragments (`j('512','994','8203')`), the existing pattern in `scripts/real-data-rules.test.ts`.
- Never paste RentCast doc examples.
- Never put `support@…` style addresses in copy.

### Pitfall 6: ESLint flat config: later `no-restricted-syntax` / `no-restricted-imports` entries REPLACE earlier options
**What goes wrong:** Adding a new config object with `no-restricted-syntax` for routes silently drops the existing fetch ban for those files. Adding a `no-restricted-imports` "don't import `lib/data/rentcast`" rule for routes gets overridden by the per-portal entries (which set their own `no-restricted-imports`).
**How to avoid:**
- Append the `$effect` selector to the **shared** `noFetch` array (rename it `restrictedSyntax`).
- Merge the new import pattern (`$lib/data/rentcast/**`, `$lib/data/fixtures/**` and the internal repos may be imported only from `lib/data/**`) **into each existing `forbid(...)` list** and into a new catch-all entry.
- Extend `scripts/eslint-rules.test.ts` with in-memory `lintText` cases. Each must fire on a violation and stay silent on the allowlist:
  - `$effect` + `gateway.get`
  - a route importing `$lib/data/rentcast/client`
  - a fetch inside a route (regression)

### Pitfall 7: CORS response headers are invisible
`Retry-After`, `X-Total-Count`, `X-Limit` and `X-Offset` are not CORS-safelisted, and RentCast sends no `Access-Control-Expose-Headers`. Code that reads them gets `null`. Backoff is the fixed 2/4/8s (cap 30s). Truncation is detected by `rows.length === limit`.

### Pitfall 8: The `404` vs `200 []` ambiguity for listing searches
The response-codes doc says a 404 means no results. The pagination doc says "continue making requests until you receive a response containing an empty array (`[]`)", which implies a billed `200 []` for an offset past the end, and possibly for some empty searches.
**How to handle:**
- Treat `200 []` as a successful empty result: billed, positive-cached for the listings TTL, rendered with the `NoResults` panel.
- Never auto-request offset pages.
- Real-key UAT records which one an empty first page returns.

### Pitfall 9: Fixture ZIPs that turn out to be real
**What goes wrong:** A "made-up" ZIP like 78799 or 73399 may be assigned now or later, so the "sample" data points at a real place.
**How to avoid:** Use **3-digit prefixes unassigned in both the USPS DMM L002 matrix and the GeoNames US postal dataset (downloaded 2026-10-04)**. Of the L002 "X" list, `569`, `851` and `876` now have ZIPs in GeoNames, so avoid them. Recommended metros (city names checked: 0 hits in GeoNames US place names):

| Metro | State | ZIP3 (unassigned) | Sample ZIPs | Why plausible |
|---|---|---|---|---|
| Harlow Springs | OK | **742** | 74201, 74203 | OK owns 730-749. 742 is a gap |
| Bayou Verde | LA | **702** | 70201, 70204 | LA owns 700-714. 702 is a gap |
| Juniper Mesa | AZ | **858** | 85801, 85806 | AZ owns 850-865. 858 is a gap |

CONTEXT's "Harlow Springs, TX" example cannot work: **Texas (750-799, 885, 733) has no unassigned ZIP3 prefix** (verified). Moving the metro to OK keeps the name and the rule "non-assigned ZIP ranges".
**Guard extension** (in `real-data-rules.mjs`, for files under `lib/data/fixtures/`):
- Every 5-digit `zipCode` value and every ZIP inside `formattedAddress` must start with one of `742|702|858`.
- Every URL host must be `example.com`/`example.org`/`*.test`.
- Every `mlsNumber` must start with `SAMPLE-`, and `mlsName` must be `"Sample MLS"`.
- Every `id` must contain one of the three ZIP prefixes.

**Coordinates:**
- Fixture lat/long are not PII, but they must not sit on real homes. Generate them around a centroid in open land.
- Mark every `formattedAddress` street with fictional street names: `"Ledgerstone Ln"`, never real street names. Real-sounding numbers on fictional streets in unassigned ZIPs cannot resolve to a real address.

### Pitfall 10: Agent names collide with real people
Generated "First Last" combinations will match real people somewhere. **Mitigation:** draw surnames from an invented list (e.g. "Quillfeather", "Ambershaw", "Tallowmere"), not a census list. Every contact is on a sample-chipped card (UI-SPEC), emails are `firstname.lastname@example.com`, websites are `https://example.com/agents/{slug}`, phones are `555-01xx` (stored as RentCast-style bare digits, e.g. `"4055550142"`, which the guard's `PHONE` regex parses as exchange 555, line 0142, allowed).

### Pitfall 11: Fixture-date decay
Absolute dates committed in 2026 make every sample listing "listed 400 days ago" in 2027, so `daysOld` filters and "new since last visit" stop working. Use Pattern 5 rebasing. Unit test: run fixture fetch with `now = anchor + 400 days` → `daysOld=*:7` still returns rows.

### Pitfall 12: The scheduler marks listings "gone" because of truncation
With fetch-wide (500 rows), a listing can drop out of the window while still active. Only mark `gone` when the new snapshot is not truncated (Pattern 7), or when the record itself shows `Inactive`/`removedDate`.

### Pitfall 13: gitleaks `generic-api-key` on test fixtures
Default gitleaks rules flag high-entropy strings assigned to names like `apiKey`. Use low-entropy obvious fakes in tests (`'test-key-not-real'`, `'k'.repeat(32)`), never random hex.

### Pitfall 14: Vitest browser mode + the fetch-ban setup file + CI order
- **Setup file:** the existing `setupFiles: ['../../tooling/vitest/no-network.ts']` overwrites `globalThis.fetch`. In browser mode, module loading uses native `import`, not `fetch`, so it should coexist. This is **MEDIUM**: prove it in a Wave 0 spike (one trivial component test green with the ban active).
- **CI order:** `ci.yml` runs `pnpm test:unit` **before** `playwright install --with-deps chromium`. Move the install step above `pnpm test:unit` in the `quality` job. `scripts/workflow-gate.test.ts` only asserts the order check → lint → unit → build and gitleaks-before-unit, so moving the install is compatible. Re-run it.
- **Config:** use a separate Vitest project `web-browser` (`include: ['src/**/*.browser.test.ts']`) so the Node `web` project is unchanged.

### Pitfall 15: Phase 3 is planned but not executed
The vault API names (`getKey`, `onChange`), the Dexie DB module, the backup registry, `LiveAnnouncer`, `ConfirmDialog` and the `testKey(provider)` hook registration are contracts from 03-CONTEXT/03-UI-SPEC, not code. **The first Phase 4 plan task should read the shipped Phase 3 code and adapt names.**
- **DB version:** add a new Dexie `version(n+1)` with Phase 4 tables. Never edit Phase 3's version block.
- **Backup registry:** `apiCache` excluded. `ledger`, `savedSearches`, `searchSnapshots` and the cap/data-source prefs included. Keys are never included.

### Pitfall 16: Overage price differs by plan
$0.20 is the Developer plan only (Foundation $0.06, Growth $0.03, Scale $0.015; rentcast.io/api). The UI-SPEC copy fixes "$0.20" and plan limit 50, which is correct for the free plan. Keep `PLAN_LIMIT` and `OVERAGE_USD` as single exported constants so a later "my plan" setting is trivial. Not in scope now.

## Code Examples

### Error classification (core, pure)
```ts
// packages/core/src/data/errors.ts
export type GatewayErrorKind =
	| 'InvalidKey' | 'RestrictedKey' | 'RateLimited' | 'BudgetCapReached'
	| 'NoResults' | 'NetworkError' | 'SchemaMismatch';
export function classifyResponse(status: number, body: unknown): { kind: GatewayErrorKind; detail?: string } | null {
	const code = typeof body === 'object' && body && 'error' in body ? String((body as { error: unknown }).error) : '';
	if (status === 200) return null;
	if (status === 401) return { kind: 'InvalidKey' };
	if (status === 403) return { kind: 'RestrictedKey', detail: code.startsWith('billing/') ? 'billing' : 'restriction' };
	if (status === 404) return { kind: 'NoResults', detail: code === 'sample/outside-coverage' ? 'outside-sample-coverage' : undefined };
	if (status === 400) return { kind: 'NoResults', detail: 'bad-request' };
	if (status === 429) return { kind: 'RateLimited' };
	return { kind: 'NetworkError', detail: status >= 500 || status === 405 ? 'server' : undefined };
}
export const backoffMs = (attempt: number) => Math.min(2000 * 2 ** attempt, 30_000); // 2s, 4s, 8s … 30s
```

### RentCast client (the only fetch call site)
```ts
// apps/web/src/lib/data/rentcast/client.ts (sketch)
export function createRentCastClient(deps: { fetch: typeof fetch; getKey: () => string | null; base?: string }) {
	return {
		async get(endpoint: EndpointId, params: CanonicalParams): Promise<RawResult> {
			const key = deps.getKey();
			if (!key) throw new GatewayError('InvalidKey');
			const url = new URL(PATHS[endpoint], deps.base ?? 'https://api.rentcast.io');
			for (const [k, v] of params) url.searchParams.set(k, v);
			url.searchParams.set('suppressLogging', 'true');
			const ctrl = new AbortController();
			const timer = setTimeout(() => ctrl.abort(), 20_000);
			try {
				const res = await deps.fetch(url, {
					method: 'GET', headers: { 'X-Api-Key': key, Accept: 'application/json' },
					credentials: 'omit', referrerPolicy: 'no-referrer', cache: 'no-store', signal: ctrl.signal
				});
				const body = await res.json().catch(() => undefined);
				return { status: res.status, body };
			} catch { return { status: 0, body: undefined }; } // NetworkError upstream
			finally { clearTimeout(timer); }
		}
	};
}
```

## Open Questions

1. **Estimates TTL: 7d (CONTEXT) vs 14d (CLAUDE.md reconciliation).**
   - Known: CONTEXT puts exact TTLs in Claude's Discretion. The UI only reads `stale`.
   - **Recommendation:** **7 days**, matching the locked CONTEXT text. Listings 24h, market stats 30d, negative (404/400) 24h. Property records (90d) are not used in Phase 4. Keep all of them in one `TTL_MS` table in core.
2. **HTTP 400 is not in the locked taxonomy.**
   - **Recommendation:** map it to `NoResults` (`detail:'bad-request'`). For AVMs it means "address could not be parsed or geolocated", which the NoResults copy ("Try a nearby ZIP… Edit search") fits. Negative-cache it 24h. Log the body's `message` to the console only, with the address redacted.
3. **Sample mode with a non-sample location.**
   - The UI-SPEC has no string for it.
   - **Recommendation:** the fixture fetch returns `404 sample/outside-coverage`, and the gateway yields `NoResults` with `detail:'outside-sample-coverage'`. Phase 4 exports `SAMPLE_METROS` so Phases 6/7 can offer them as one-tap locations, and adds the copy in their UI-SPECs. Phase 4's `GatewayError` keeps the standard NoResults copy.
4. **`DueSearchesDialog` cost vs count.**
   - Batch cost can be lower than the number of searches (shared keys).
   - **Recommendation:** pass `estimateBatchCost` into `CostLabel`, giving "Check 5 searches (2 calls)". The UI-SPEC string is "Check {k} searches ({k} calls)", and the cost part is the CostLabel's job, so this stays inside the contract. Flag it to the UI checker if it is strict.
5. **Renewal day.**
   - **Recommendation:** calendar month UTC now (`periodKey(now, renewalDay = 1)`, already parameterized). No setting in v1. The scope note copy already discloses the mismatch.
6. **Unknown-status (`0`) calls.**
   - A request might reach RentCast and the response be lost.
   - **Recommendation:** count it as unbilled (UI copy says "Tran didn't count a call"), and record `status: 0` so a future policy can count it.
