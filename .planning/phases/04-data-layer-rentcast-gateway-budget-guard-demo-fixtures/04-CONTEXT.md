# Phase 4: Data Layer: RentCast Gateway, Budget Guard & Demo Fixtures - Context

**Gathered:** 2026-10-04
**Status:** Ready for planning

<domain>
## Phase Boundary

One `DataGateway` is the sole path to RentCast. It owns:
- canonical request keys and in-flight dedupe
- an IndexedDB cache with per-endpoint TTL and "as of" stamps
- a monthly call ledger with a user-editable hard cap (default 40 of 50) and an explicit confirm step past it
- an error taxonomy with specific user messages
- provenance on every row (`{source: 'rentcast' | 'sample', fetchedAt, stale}`)

The phase also ships RentCast-shaped synthetic fixtures for every portal (badged "Sample data"), zero-cost key validation, and the shared check-on-open alerts scheduler (`core.diffSnapshots` + two-cursor TTL re-run) that Phases 6 and 7 consume.

Requirements: DATA-01..05. Portal UIs that *use* the gateway belong to Phases 6-9; this phase delivers the gateway, the fixtures, the meter/cost/cap UI primitives and the Settings "Test key" integration.

</domain>

<decisions>
## Implementation Decisions

The owner chose fully autonomous mode on 2026-10-04. Researched recommended defaults are adopted.

### Gateway & budget
- **Single gateway module** at `apps/web/src/lib/data/` wrapping a typed RentCast client (`X-Api-Key` header only; GET only; Zod-mini response schemas; mappers to normalized domain rows in `packages/core`).
- **Budget math lives in `packages/core`** (pure, tested): ledger of billed calls per calendar month (UTC, matching RentCast's cycle approximation), cap check, projected-burn estimate.
- **Only HTTP 200 responses count as billed** (RentCast bills successful requests). 404 "no results" is negatively cached for its TTL and recorded as unbilled unless Phase 4 research with a real key proves otherwise; the ledger stores both counts so the policy can flip without a migration.
- **Hard cap:** default 40 of 50, user-editable in Settings (1..50; values above the plan limit need a typed confirmation). When the next call would exceed the cap, the gateway throws `BudgetCapReached`; the UI shows a confirm dialog ("This call goes past your cap. RentCast bills overage at $0.20 per call.") with an explicit "Spend 1 call anyway" action. Confirmation is per call, never remembered.
- **Call cost preview:** every call-spending control carries a `(N calls)` label derived from the gateway's `estimateCost(request)`; reads served from cache show `(0 calls · cached)`.
- **No auto-pagination, no reactive refetch.** `$effect` must never call the gateway directly; views read from cache-backed stores and only explicit user actions (search, Refresh, scheduled alert run) spend calls. A lint rule / unit test guards this.
- **Cache:** Dexie table `apiCache` keyed by canonical request key; per-endpoint TTLs (listings 24h, estimates 7d, market stats 30d, 404 negative 24h). "Refresh (1 call)" bypasses TTL for one request.
- **Alerts scheduler:** on app open, saved searches with `lastRunAt` older than 24h are due; they run sequentially, each at most once per 24h, and if more than 3 are due the user confirms the total cost first. Diffing (`new / price-changed / gone`) is `core.diffSnapshots`.
- **Call-count tests (unit, fake-indexeddb, mocked fetch):** 60 simulated calls block #41; re-rendering a view 10× spends 0 extra; 5 due saved searches on open run each exactly once; identical repeat request spends 0 and carries the original `fetchedAt`.

### Key validation & errors
- **Zero-cost "Test key":** format check, then a deliberately empty/unsatisfiable query expected to 404 (valid key), 401 (invalid), 403 (restricted/billing). Result labels: valid / invalid / restricted. Falls back to "could not verify (network)" on CORS/network failure. Plugs into Phase 3's `testKey('rentcast')` hook.
- **Error taxonomy** (`core`): `InvalidKey` (401), `RestrictedKey` (403), `RateLimited` (429, with backoff hint), `BudgetCapReached`, `NoResults` (404), `NetworkError`, `SchemaMismatch`. Each maps to one specific plain-language message and, for 401/403, a link to Settings.

### Sample data (demo mode)
- **Synthetic fixtures** generated by a seeded deterministic script (`scripts/gen-fixtures.mjs`) into `apps/web/src/lib/data/fixtures/*.json`: 3 fictional metros (invented city/zip names that do not exist, e.g. "Harlow Springs, TX 7xx99"-style with non-assigned ZIP ranges), ~60 rental listings, ~40 sale listings, rent/value estimates, zip market stats with 24-month history, dated price events.
- **No real addresses, names, phones, emails, MLS numbers.** Agent contacts use `example.com` and 555-01xx numbers. The existing CI real-data/PII guard (`scripts/guard-real-data.mjs`) must pass on all fixtures; a planted-PII test proves the guard fails when it should.
- **Fixture adapter** implements the same gateway port as the live client; selection is automatic: no RentCast key → sample mode; key present → live mode, with the user able to force sample mode in Settings.
- **"Sample data" badge** (provenance chip) appears on every surface rendering fixture rows; live rows show "RentCast · as of {relative time}" and a "stale" variant past TTL.

### UI primitives (consumed by portals)
- `CallMeter` (header/Settings: "12 of 50 calls this month", cap marker, resets on the 1st), `CostLabel`, `CapConfirmDialog` (accessible, focus-managed, no `window.confirm`), `ProvenanceChip`, `GatewayError` (message + action). Styled with Phase 2 tokens.

### Claude's Discretion
- Exact TTL values within the ranges above; canonical key hashing; Dexie table/index layout; fixture record counts; whether the ledger resets on calendar month or a user-set renewal day (default calendar month, renewal-day setting optional).

</decisions>

- Settings page (Phase 3): RentCast key field gains "Test key" result, cap editor, sample-mode toggle, CallMeter.
