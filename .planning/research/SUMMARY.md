# Project Research Summary

**Project:** Tran Real Estate Tools, milestone v1.1 "Launch & Hardening"
**Domain:** Go-live, post-deploy verification, test-suite hardening, framework-major migration and $0 extension release for an existing, feature-complete static SvelteKit + MV3 monorepo (no new end-user features)
**Researched:** 2026-10-29
**Confidence:** HIGH (versions, Kit 3 / Vitest 5 / pnpm 12 facts, Pages and Edge mechanics, repo touchpoints verified today); MEDIUM for CI post-deploy mechanics and CDN propagation; LOW only for flake-budget numbers and X/iMessage share-card behaviour

> This SUMMARY covers only what is new for v1.1. The v1.0 research (and the reconciliation rules copied into `CLAUDE.md` under "Research Reconciliation Overrides") is archived in `.planning/milestones/v1.0-research/` and still governs the product. Nothing here reopens a v1.0 decision.

## Executive Summary

v1.0 shipped on 2026-10-29 as a locally verified build (6,647 unit tests, 2,327 E2E, launch audit all PASS) with **no git remote and no origin**. v1.1 is an operations milestone, not a product milestone: its job is to take that build live on `tranrealestate.github.io`, make every future deploy prove itself, and clear the debt and toolchain drift carried out of v1.0. Teams that do this well treat it as three separable concerns: a small, read-only, un-mocked **post-deploy smoke** that runs against any origin from an environment variable; a **deterministic pre-deploy suite** where wall-clock budgets live in a serial lane and retries are a measurement tool, never a fix; and a **framework-major migration done alone**, on a suite already proven green, one tool per commit. All four research files converge on the same shape and the same order.

The recommended approach, continuing from Phase 12: build the smoke suite **before** the origin exists (the local Pages emulator `scripts/serve-pages.mjs` already reproduces Pages' 301/200/404 contract), clean the history, then let the owner create the org and push with `PAGES_ENABLED` unset so the first-ever GitHub run of `ci.yml` surfaces runner-specific surprises without a deploy attached. Phase 13 flips the variable, observes the first deploy, chains the live smoke behind it (polling `/_app/version.json` for the expected SHA because Pages serves through Fastly with `max-age=600`), and burns the 77 HUMAN-UAT rows down to the ~20-25 that truly need an account, a device or a judgement. Debt (14) and lanes (15) follow, then the toolchain phase (16) migrates pnpm 11 -> 12, SvelteKit 2 -> 3 and Vitest 4 -> 5 as three single-purpose plans with `pnpm verify` + `pnpm smoke:local` after each and a green live smoke as the exit gate. The extension release (17) needs only the live privacy URL and floats after 13. SvelteKit 3.1.0, adapter-static 4.0.0, Vitest 5.0.5 and pnpm 12.16.1 are all stable `latest` today; Kit 3 clears three of the four low audit exceptions (`deepmerge` via `vite-plugin-svelte` stays until 2027-01-31).

The risks are concrete and mostly pre-push. (1) 145 commits from 2026-10-13..14 still carry an AI co-author trailer; the rewrite must happen before `git remote add`, and `.gitleaks.toml`'s two SHA-allowlisted commits must be re-derived afterwards or the first `hygiene` run goes red. (2) Kit 3 removes `kit.serviceWorker.files`, so the `.nojekyll` dotfile filter must move into the worker itself; otherwise the service worker fails to install **only on the live origin** (the emulator serves dotfiles), which is exactly why the live smoke must gate the Kit 3 deploy and why `serve-pages.mjs` must 404 dotfiles before the migration. (3) `docs/DEPLOY-CHECKLIST.md` names the wrong Umami host; the real collect endpoint is `https://gateway.umami.is/api/send`, and the beacon's `no-cors` mode hides the 404. (4) Umami Hobby has no API and Web3Forms has no sandbox, so pageview receipt and form delivery stay owner UAT rows; the smoke proves them at the HTTP layer only and must never submit a form or spend a provider call. Every one of these has a named prevention phase below.

### Architecture Approach

v1.1 maps six capabilities onto the architecture that shipped, adding files beside existing ones rather than editing the gated core. The governing pattern is **"smoke = existing E2E oracles re-pointed at a URL, never new assertions"**: `tests/smoke/*.smoke.ts` under a second Playwright config with no `webServer`, importing `ROUTES` from `tests/e2e/routes.ts` and `checkHtml()` from `scripts/assert-csp.mjs`, so the CSP policy and route list have no third copy. Cross-package constants keep the repo's convention of **literal duplicate + parity test** (`TRAN_ORIGIN` vs `DEFAULT_SITE_ORIGIN` get `scripts/origin-parity.test.ts`, never a shared runtime package, because `site-config.js` must stay plain Node JS and the extension bundle must stay free of web-app code). Lanes are **additional Vitest projects** (`core-serial`, `web-serial`, `scripts-serial`, `web-browser-serial`) selected by `--project '*-serial'` / `'!*-serial'` in `package.json`, so `ci.yml` keeps its single `run: pnpm test:unit` line and `workflow-gate.test.ts` stays true. Every workflow change is a **two-file commit** (workflow + its gate test), because `workflow-gate.test.ts` pins exactly 7 `uses:` lines, 2 checkouts and 2 `PAGES_ENABLED` gates in `ci.yml` and `extension-release-gate.test.ts` pins the release step order. See `ARCHITECTURE.md` Section 6 for the full Kit 3 touchpoint inventory (K1-K15) and Section 7 for the release-workflow gap list.

**Major components:**
1. **Live-origin smoke suite** (`apps/web/tests/smoke/`, `apps/web/playwright.smoke.config.ts`, `scripts/smoke.mjs`, `pnpm smoke:local` / `pnpm smoke --base <url>`): routes, headers (CSP via `checkHtml`), PWA (SW registers, `caches.keys()` has `tran-shell-<sha>`, precache has no dotfiles), SEO (sitemap 14+ URLs on this origin, robots `Sitemap:`, `og/*.png` 200 `image/png`, 1200x630), third-party (no cross-origin request except the configured analytics host), analytics (one beacon POST whose URL origin equals the configured host and returns JSON, skipped when unset), extension-link (`/legal/privacy/#browser-extension` anchor present). Fresh contexts, GPC injected by default, `api.web3forms.com` route-aborted with a zero-request assertion, provider hosts aborted via the existing `support/network.ts` with `NON_LOCAL` parameterised.
2. **Post-deploy wiring**: `kit.version.name = process.env.GITHUB_SHA` (deterministic, read in config, no `ci.yml` edit); a **separate** `.github/workflows/live-smoke.yml` triggered by `workflow_run` on `ci.yml` completion for `main` plus `workflow_dispatch` with a `base_url` input; expected SHA from `github.event.workflow_run.head_sha`; origin derived from the repo owner (`https://<org>.github.io/`) or the `PUBLIC_SITE_URL` variable; only the three actions already SHA-pinned in `ci.yml`; a new `scripts/live-smoke-gate.test.ts` mirroring `workflow-gate.test.ts`. A red smoke is an **alert after deploy**, not a gate, and the workflow comment says so.
3. **Origin parity test** (`scripts/origin-parity.test.ts`): `TRAN_ORIGIN === DEFAULT_SITE_ORIGIN === resolveSiteOrigin({})`, `PRIVACY_URL` equals the privacy anchor on that origin, the anchor id exists in the page source, the listing copy and install guide carry exactly that URL, planted-mismatch non-vacuity; refactor the two hard-coded literals in `extension-docs.test.ts:103` and `assert-extension.test.ts:74,412` to import `PRIVACY_URL`.
4. **Backup round-trip spec** (`tests/e2e/backup-roundtrip.spec.ts` + `helpers/seed-all.ts`): raw-IDB seed one schema-valid row in every registered table (18; `meta` and `apiCache` excluded), export through the real Settings button, import in a fresh context through the real `#backup-file` input, assert equality per table; equality oracle derived from `objectStoreNames` minus the two exclusions so a future unregistered table fails; one documented `test.setTimeout(180_000)`, never raised later.
5. **Test lanes** (`vitest.config.ts` + four `*.serial.config.ts` + `scripts/test-lanes.test.ts`): serial membership for `fair-housing/mutation.test.ts`, `numbers.property.test.ts`, `leads/parse-freeform.test.ts`, `studio/boundaries.test.ts`, `scripts/precommit.test.ts`, `ResultsView.browser.test.ts` (renamed `*.serial.browser.test.ts`); the guard fails on any wall-clock assertion, `spawnSync`, or timeout above 15 s outside a serial include, and on any serial include that does not exist. A sibling guard asserts every Playwright/Vitest-browser config carries the Windows `System32` PATH block.
6. **Toolchain migration** (Phase 16, three plans): pnpm 12 (pin + regenerated two-document lockfile + supply-chain test rewrite + literal removal) -> Kit 3 (K12 pins -> `sv migrate` task groups -> config extraction into a plugin-free `apps/web/kit.options.js` spread into `sveltekit(kitOptions)` so `csp-policy.test.ts` and `service-worker-guard.test.ts` keep importing a plain module -> `src/service-worker/index.ts` with the dotfile filter in the worker and the guard's REQUIRED/FORBIDDEN lists flipped -> `#lib` in the five config/test files and both Vitest alias blocks -> planted-violation sweep over every `no-restricted-imports` group -> three builds + `csp:assert`, `seo:assert`, `budget:assert` -> audit exceptions 4 -> 1) -> Vitest 5 (`await render(`, `toHaveTextContent` strictness, `clearMocks: true`, `vi.mock` top-level check, `.vitest/` in `.gitignore`, `--outputFile.json=` form verified, `groupOrder` experiment for the lanes).
7. **Extension release** (`extension-release.yml` + gate test, `apps/extension/CHANGELOG.md`, `apps/extension/scripts/make-screenshots.mjs` capturing the synthetic `e2e/zillow-page.ts` fixture at 1280x800 into `store/screenshots/`, `edge-listing.md` additions, `DEPLOY-CHECKLIST.md` Step 9 rewritten to "upload the Release zip, never a local build").

### Critical Pitfalls

Top five of seventeen in `PITFALLS.md`; each has a prevention phase and a verification line in its "Pitfall-to-Phase Mapping" table.

1. **145 AI co-author trailers and a SHA-based gitleaks allowlist go public on the first push** (Pitfall 1): rewrite history before `git remote add` (`git filter-repo --message-callback` or `filter-branch --msg-filter`), assert `git log --format='%(trailers:key=Co-Authored-By)' | grep -c .` is 0, triage the 168 body mentions as a reviewed list (model IDs that are product content stay), re-derive the two `.gitleaks.toml` commit SHAs by subject or switch the allowlist to path + regex, remap hashes quoted in `MILESTONES.md` and SUMMARY files by subject, add a CI hygiene step that fails on any trailer in `origin/main..HEAD`. Never push first and clean later.
2. **Kit 3 drops `kit.serviceWorker.files`, so `.nojekyll` enters the precache and the worker fails to install only on the live origin** (Pitfall 12 / F3): filter dotfiles inside the worker (`assets.filter(a => !/(^|\/)\./.test(a.path))`), re-point `service-worker-guard.test.ts` at the worker source, make `serve-pages.mjs` 404 dotfiles **before** the migration (Debt phase) so `pwa.spec.ts:34` can catch it locally, and verify `caches.keys()` on the live origin contains `tran-shell-<sha>` after the Kit 3 deploy. This is the one Kit 3 change the live smoke must gate.
3. **The smoke asserts the CDN cache or the previous deploy** (Pitfall 3): Pages serves via Fastly with `Cache-Control: max-age=600`; set `kit.version.name` to `GITHUB_SHA` before the first deploy, poll `/_app/version.json?_=<sha>` with `cache: 'no-store'` until it matches (bounded ~12 min, distinct exit code for "not propagated" vs "failed"), never retry the job to paper over propagation, and assert CSP from the `<meta>` only (a `content-security-policy` **header** means you are looking at GitHub's own 404 page).
4. **Umami beacons go to the wrong host or are dropped as bot traffic, and the owner's stale service worker makes it look like a CSP bug** (Pitfalls 4 and 5): fix DEPLOY-CHECKLIST 8.1.2 to `https://gateway.umami.is` (the Cloud script's real collect host; `POST cloud.umami.is/api/send` is 404 and `no-cors` hides it), verify with a `curl -X POST` that returns JSON with `cache`, assert the beacon's URL origin in the smoke, keep dashboard receipt an owner row from a normal (non-headless, fresh-profile) browser, and write "open an InPrivate window" into every post-redeploy UAT row. Umami drops `HeadlessChrome` with a 200, so automation can never prove receipt.
5. **Load flakes "fixed" with timeouts, retries and worker counts that match one machine; the saved-search race fixed in the spec instead of the scheduler** (Pitfalls 10 and 11): lanes split by what they measure, `workers` derived from cores/4 locally and 2 in CI, `expect.poll` for anything set by a route handler, reproduce under injected delay before calling anything a flake; for `renter-saved.spec.ts:83`, owner decision first (keep `ifAvailable` vs bounded `AbortSignal` wait), RED-first unit test, then mutation-test the lock, the claim-then-run transaction and the bounded wait, and re-run the Phase 4 two-tab call-count proofs before touching the E2E.

Also carried prominently: **the Search Console HTML-file method breaks `csp:assert`** (use the meta tag after `%sveltekit.head%`, Pitfall 7); **GitHub push protection scans the first push with a different ruleset than gitleaks** and blocks Anthropic/OpenAI key shapes by default (grep-guard the tree for provider prefixes, Pitfall 8); **Edge certification fails on prose, not code** (no other browser names in `edge-listing.md`, notes for certification, data-usage checkboxes matching the privacy page, Pitfall 15); **the Release zip, the store zip and `HEAD` can be three artifacts** (ancestor check, upload only the Release zip, Pitfall 16).

## Implications for Roadmap

Phases continue from Phase 12. The two owner decisions in `PROJECT.md` are honoured literally: go-live is **early** (the owner gate closes Phase 12, the first deploy opens Phase 13) and Kit 3 is **its own phase after debt** (Phase 16, after 14 and 15, and after the live origin exists so the migration has a real acceptance gate).

### Phase Ordering Rationale

- **Smoke before origin, origin before everything else.** `serve-pages.mjs` already emulates Pages, so the suite is buildable now; the owner gate at the end of Phase 12 delivers the early go-live the owner asked for with the suite ready to measure it. Phase 13 then absorbs the first-GitHub-run unknowns in isolation.
- **Debt and lanes before the toolchain, in that order.** Debt touches behaviour and must not be rebased through a 1,100-import codemod; lanes give the migration a deterministic oracle. Lanes must be defined on Vitest 4 because Vitest 5 changes the pool/`projects` surface.
- **Toolchain as a single-phase wave with Kit 3 in the middle.** pnpm first (smallest blast radius, CI follows automatically), Kit 3 second (verified by the unchanged Vitest 4 harness and by the live smoke, which is the only place the service-worker change is observable), Vitest 5 last (test semantics only, against an already-accepted app). Three of four audit exceptions clear well before 2027-01-31.
- **Extension release floats.** Like Phase 11 in v1.0, it is off the critical path; its only hard dependency is the live privacy anchor, and its external wait (Edge certification) should never block another phase.
- **Every workflow edit is a two-file commit** (workflow + gate test), and the live smoke lives in its own workflow so `ci.yml`'s pinned counts never move for a non-CI reason.
